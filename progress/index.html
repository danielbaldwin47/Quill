The page

Paper, margins, measure, scrolling, the empty state

Picked blind 1

Biggest gapHeadings don't hang their markers: A's `##` sits at x=694, flush with the body's left edge (694–697), so the heading's actual words start at x=775 — 81px (≈40 CSS px, 3.3 characters) inside the column. B outdents `##` to x=619 so "1. Down the Rabbit Hole" lands on the same 691px edge as the prose. Every heading in A therefore puts a visible step in the left edge; the one line on the page that should anchor the column is the one line that doesn't.

A is the page you can actually write on: neutral #f9f9f9 paper, a dead-straight body edge at 694px, and a three-step focus ramp (#cccccc far context → #b2b2b2 approaching the caret → #1c1c1c live sentence) that tells you where you are without shouting. B throws that away for a rainbow — a quarter of the ink you're currently typing rendered in ochre, blue and green, plus a struck-through word — which is a syntax highlighter's idea of calm, not a writer's. B also can't hold its measure: its italic isn't metric-compatible with its roman, so the wrap boundary jumps from x≈2176 in the emphasised block to x≈2225 in the plain one, a 49px (≈2 character) swing down the page, where A's two blocks agree to 1px (2213 vs 2212). B wins the hanging `##` and gives marginally more air (line pitch 73.3 vs 72, ≈1.81 vs 1.74 line-height), and neither app dims its markdown markers at all — but a 40px heading step is a flaw you stop seeing by page three, and coloured words under the caret is one you never stop seeing.

BuilderRebuilt app/css/page.css around measurements of the iA window (column 768 logical px = 64 chars, margins 347 each side, first ink 85px below the editor top, blank line = exactly one pitch): the page now centres type.css's 64ch measure and opens the document two line-pitches from the top instead of the old 40vh slab, so the first sentence lands under your eyes; typewriter mode swaps to 52vh/62vh padding so any line can still reach the middle. Added scroll-padding (10vh/28vh) — verified Chromium honours it for textarea caret scrolling, so typing at the end of a document rests at ~69% of the window instead of the bottom edge — plus scrollbar-gutter: stable both-edges so the column never shifts sideways when a doc grows past one screen (measured left 336.0 / right 336.0 both ways), and a faint ":has()"-driven "Start writing…" on the empty page, sitting exactly where the first glyph will land (A/B'd: no typing-latency cost). Ours now matches the reference to within 2 logical px on first-ink height and 1px on column edges; remaining differences in the pair are other pieces' (syntax colours, hanging ## which this architecture cannot do).

Cursor & caret

Shape, color, blink, motion, selection

Picked blind 1

Biggest gapA gives the selection two identical 4px caret bars, one at each end (device runs x426–433 and x734–741, both 8×92px, both #00B5FF at 100% alpha) — nothing distinguishes anchor from focus, so the caret stops meaning "where I am" and there is no cue which edge shift+arrow will move. B at least differentiates its two ends (handle above-left vs below-right).

The light-mode carets are effectively the same object in both — 8–9 device px (4 CSS px) of flat #00B5FF spanning the full 92px line box, a bar twice the width a text caret should be and tall enough to overshoot the ascender, so neither wins there and both read as a block, not a hairline instrument. The dark selection decides it: B hangs 22px touch-style dots off both ends of the range, which collide with the lines above and below and turn a keyboard selection into a phone gesture, and then dims and strikes the selected word down to 2.7:1 so you cannot read the thing you are about to replace. A's version is dumber but honest — the word stays at 7:1, nothing overlaps the neighbouring lines, and the range edge is the same 4px bar as the caret. A's real sin is that the two edge bars are identical, so the caret loses its one job of telling you where the next keystroke lands.

BuilderRebuilt the caret from re-measured iA pixels: #00b5ff, 0.155 em wide snapped to whole CSS px, height = full line pitch, and the band anchored 68.75% above / 31.25% below a runtime-measured baseline (iA sits lower than a CSS line box, centred on the ink rather than the em box), with the left edge nudged 0.07 em past the advance cell so it lands where the next glyph's ink begins; it rests on left/top rather than a transform so both edges are hard device pixels. Focus & typewriter

Sentence/paragraph dimming, typewriter line

Picked blind 1

Biggest gapThe caret — the one thing focus mode exists to point at — is soft and off-grid. A's caret measures 4x55 device px at 2x DPR but straddles a pixel boundary: columns 1842-1844 are solid #00b5ff, column 1845 is a partial at ~69% coverage, and the top/bottom rows are 63%/34% alpha, so it renders as a fuzzy ~1.75 CSS px sliver 27.5 CSS px tall (76% of the 36.4px line box). B's is exactly 6x70 device px of #00c3ff with zero partial pixels — 3 CSS px, 95% of the line box, hard-edged. Secondary but on the same wound: A leaves the '#'/'##' inline at x=643, so heading text starts 48px (2 chars) right of the body's left margin, while B hangs the markers (x=500 and x=476) and lands the heading text flush at 551 with the body.

A wins, but only because it actually understands what a sentence is: its dimming steps at the full stop, not at a line, so the sentence behind you and the sentence ahead stay at 4.9:1 while the page falls to 3.57:1 — B just slams everything that isn't the live sentence to one flat #707070 and lets you write into a void. The cost is that A's caret, the anchor the whole mode is built around, is a half-pixel-straddling 1.75px smear with 63%/34% alpha at its ends, next to B's crisp 3x35 CSS px bar; and A leaves its hashes inline so the headings sit 2 characters proud of the body margin that B keeps flush. Neither one is doing typewriter scrolling here — both are parked at the document top with the H1 clipped 2-4px from the window edge, and the active line lands at 49.9%/50.2% by accident of passage length, not by any lock. Both also dim the headings to the same #707070 as distant body text, so the moment you enter focus the document loses its skeleton.

BuilderDimming now reads theme.css's --fg-dim directly, so it is iA's measured #cccccc/#707070 exactly (dark was previously ~#434343 — far too dead). Typewriter replaced with a retargetable rAF ease (120ms for a one-line advance, capped 280ms) that never fights manual scrolling, centres exactly at 0.50 on keyboard moves, and on a click only nudges to the nearest 18/82% band edge instead of throwing the page — the "screen jumping" iA's own docs warn about. Per-keystroke cost +0.3ms over focus-off (p50 1.6ms); verified in both themes, auto, and all three fonts.
